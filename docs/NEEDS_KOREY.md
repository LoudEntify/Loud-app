## Blocking Phase 1 (staging can't go live without these)

- [ ] **Create the new staging Supabase project.** Go to supabase.com/dashboard → New Project → name it `loudentify-staging` → region: pick London/UK if offered, otherwise an EU region (per `docs/CLAUDE.md` §2, this must be a separate project from the frozen pilot one — do not reuse it). Once created, go to Project Settings → API and copy: the Project URL, the `anon` public key, and the `service_role` key. Go to Project Settings → Database and copy the project reference (the short ID in the URL, e.g. `abcdefghijklmnop`) and set/copy the database password. You'll paste all of these into GitHub in the next step.
- [ ] **Create the new production Supabase project.** Same steps as above, name it `loudentify-production`, same region. Keep this one's credentials separate — they go in a different place (see below) and this session never touches them, per `docs/CLAUDE.md` §2 ("you only ever hold STAGING credentials").
- [ ] **Create two GitHub Environments on the repo** (github.com/LoudEntify/Loud-app → Settings → Environments → New environment): one named exactly `staging`, one named exactly `production`. On `production`, tick "Required reviewers" and add yourself (and Ugo, if he should also be able to approve). This is the "one approval click" `.github/workflows/promote.yml` waits on — without this setting, promote.yml will run production deploys with no human gate at all, which defeats the point, so don't skip it.
- [ ] **Add these secrets to the `staging` GitHub Environment** (same Settings → Environments → staging → Environment secrets): `SUPABASE_ACCESS_TOKEN` (create at supabase.com/dashboard/account/tokens — this is account-wide, see the note below), `SUPABASE_STAGING_PROJECT_REF`, `SUPABASE_STAGING_DB_PASSWORD`, `VERCEL_TOKEN` (create at vercel.com/account/tokens), `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` (both from the Vercel project's Settings → General, or `vercel project ls`), `STAGING_ALIAS_DOMAIN` (e.g. `staging.loudentify.app` — needs a DNS record pointed at Vercel first), `STAGING_SMOKE_EMAIL` / `STAGING_SMOKE_PASSWORD` (a throwaway test account — Claude Code can create this one itself once staging exists, via the normal sign-up form, same pattern as `docs/SMOKE_TEST.md` describes for the pilot), `VERCEL_AUTOMATION_BYPASS` (Vercel project → Settings → Deployment Protection → Protection Bypass for Automation — copy the value).
- [ ] **Add these secrets to the `production` GitHub Environment**: `SUPABASE_PRODUCTION_PROJECT_REF`, `SUPABASE_PRODUCTION_DB_PASSWORD`, `PRODUCTION_SMOKE_EMAIL` / `PRODUCTION_SMOKE_PASSWORD`. (`SUPABASE_ACCESS_TOKEN`, `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` can be the same values as staging's, added again on this environment — those tokens authenticate the CLI, they don't by themselves pick which project gets touched; the project ref and password are what actually scope each run to staging vs production.)
- [ ] **Important nuance on "staging credentials only":** a Supabase personal access token (`SUPABASE_ACCESS_TOKEN`) is account-wide — it can see every project in your Supabase account, not just staging. The actual isolation in `.github/workflows/staging.yml` vs `promote.yml` comes from which project ref and DB password get passed to `supabase link`, not from the access token itself. If you want a harder guarantee that a staging-side credential leak can never touch production, put staging and production in **separate Supabase organisations** with separate accounts/tokens — `docs/ARCHITECTURE.md` says this is "ideally" the setup. If that's more than you want to do right now, same-org-separate-projects is the minimum and is what the workflows above assume.
- [ ] **Branch protection on GitHub**: Settings → Branches → add a rule for `staging` requiring the `ci` check to pass before merging, and a rule for `main` blocking direct pushes (promote.yml is the only thing that should ever write to `main`). This session created a `staging` branch and pushed a `feature/phase1-foundations` branch directly (see `docs/DECISIONS.md`, 1 Oct) because no `gh` CLI or GitHub token was available to open a real pull request — once this protection and a token exist, future sessions should go back to the PR flow `docs/CLAUDE.md` describes.
- [ ] **Give Claude Code a way to open real pull requests.** Either install and authenticate the `gh` CLI in this environment (`gh auth login`), or provide a fine-grained GitHub personal access token with `pull_request` write scope as an environment variable. Without one of these, every future session has to merge branches directly with `git`, which is what this session did, logged as a deliberate deviation in `docs/DECISIONS.md`.

## Blocking Phase 3 (YouTube delivery)

- [ ] **Start Google OAuth verification now, not when Phase 3 starts.** `docs/YOUTUBE_ADDENDUM.md` and `docs/ARCHITECTURE.md` v2 both flag this: the YouTube Live Streaming scope is a "sensitive scope" under Google's OAuth verification process, which has its own lead time (can be days to weeks) separate from engineering work. Steps: create a Google Cloud project, enable the YouTube Data API v3 and YouTube Live Streaming API, configure the OAuth consent screen, and submit for verification requesting the live-streaming scope. The sooner this is submitted, the less likely it blocks Phase 3's finish date.
- [ ] **Default YouTube API quota may be too low.** Once the Google Cloud project exists, check the default quota against the planning basis in `docs/YOUTUBE_ADDENDUM.md` ("up to 400 viewers per artist across 100+ concurrent streamers") and request a quota increase early if the default looks tight — this is also a request with its own lead time.
